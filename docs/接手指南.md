# 接手指南

写给会提需求、让 AI 写代码，但自己不做安卓开发的维护者。通用的 Android 知识这里不讲，只讲这个仓库特有、不知道就容易出错的地方。

现状、发版和待办在 [HANDOVER.md](../HANDOVER.md)，仓库约定在 [AGENTS.md](../AGENTS.md)，构建在 [BUILD.md](../BUILD.md)。本文讲背景和常见的坑。

## 1. 项目是什么

- dsh（DeepSeek Harness）是跑在 Node.js 上的 agent 框架。
- DSHA 把 Ubuntu rootfs 解压到 App 私有目录，用 proot / proroot 在没有 root 的手机上跑 Node 24 + dsh，再用内置浏览器打开 dsh 的网页界面。
- DSHA 自己是宿主：装环境、起停进程、备份恢复，并把 Android 能力（通知、悬浮条、ADB/Shizuku/Root、无障碍、文件）交给 agent。

分层：

```
原生界面（Java，ui/、res/）
    ↓
core/HarnessController 等编排类
    ↓ 起进程、执行命令
proot / proroot 容器：Ubuntu + Node 24 + dsh
    ↓
本机端口：3180 dsh 网页 · 3190 App 能力桥 · 3181 局域网代理（只在 `util/Constants` 定义一次）
```

改东西之前，先想清楚改的是哪一层。

## 2. 职责边界

dsh 已经有的功能，DSHA 不再做一遍。

| 属于 dsh，不要碰 | 属于 DSHA |
|---|---|
| 权限档位、会话与恢复、上下文压缩、技能、任务调度、模型与账号、MCP、记忆、消息分支 | 容器与 rootfs、运行时升级、Android 集成（悬浮条、通知、设备通道、无障碍、终端、端口桥）、凭据与配置、备份恢复、插件安置、应用内更新与签名 |

参考别的项目提新功能前，先确认 dsh 本身有没有。

## 3. 环境与验证

- 手机容器里没有 Android SDK，编不了 APK，结果以 GitHub Actions 的 Build APK 为准。
- 有完整工具链的电脑上用 `bash build.sh`（默认 `:app:assembleStandardDebug`）和 `bash build.sh :app:testStandardDebugUnitTest`。它会自己找 JDK 17 和 SDK，并按可用内存设置 Gradle 堆。
- aarch64 主机跑不了 aapt2 时，用 `python3 tools/run-unit-tests.py` 直接跑纯逻辑单测。它是
  kotlinc + javac 混编的，`.java` 和 `.kt` 都认；`DSHA_ONLY=QueryTest,ShellQuoteTest` 可以只跑几个。
  它会校验本机 `kotlinc` 与 AGP 内置的 Kotlin 同版本，不一致直接报错（见 [kotlin-migration.md](kotlin-migration.md)）。
- `tools/` 下还有很多 `test-*.py` / `.mjs`，哪些能在 CI 或容器里跑见 HANDOVER.md 第 8 节。

改完就验证，不要攒着。AI 说「修好了」的时候，问它跑了什么、结果是什么。

## 4. 代码地图

`app/src/main/java/com/deepseekharness/app/` 的分包见 AGENTS.md。几个最常打交道的类：

| 类 | 管什么 |
|---|---|
| `core/HarnessController` | 启停 dsh、捕获鉴权链接。已经很大，新逻辑写成独立的类 |
| `core/ConfigStore` | 配置唯一的读写入口 |
| `HttpShellService` | 设备桥，agent 调 Android 能力都从这里进 |
| `runtime/ProotBootstrap`、`runtime/ContainerRuntime` | 拼 proot 命令、bind 列表 |
| `runtime/WebProcessManager` | 停止 dsh 进程 |
| `backup/` | v5 加密备份，格式见 [backup-format-v5.md](backup-format-v5.md) |

`util/` 里放纯逻辑类，不能 import Android API（`tools/test-architecture-boundaries.py` 会检查），每个都有对应的单测：

| 类 | 管什么 |
|---|---|
| `ShellQuote` | 把字符串安全地拼进 shell 命令（POSIX 单引号） |
| `Query` | 解析 URL 查询串，参数名精确匹配 |
| `GitHubRef` | 解析 GitHub 链接，保留分支和子目录 |
| `BackupScope` | 备份范围和文件名前缀 |
| `WebProcSel` | 认出 dsh 进程，不误判 proot / proroot |
| `DeviceShellPolicy`、`SmsQuery` | 设备命令和短信查询的白名单 |
| `BridgePathPolicy` | 桥的导出 / 读文件路径限制 |
| `PluginInstallLink` | 网页发来的插件下载请求 |
| `AutomaticBackupPolicy` | 自动备份时间计划 |
| `PictureInPicturePolicy` | 画中画进入条件和比例 |

新功能的默认做法：判断逻辑抽进 `util/` 并写单测；界面、权限、文件系统那部分留在原处，那部分只能真机验证。

## 5. 常见的坑

让 AI 写代码时，可以把这一节直接贴给它。

### 同一个判断写在多个地方

最常见的问题。同一个判断写了两份，改了一份，另一份还是旧的。上面 `util/` 那张表里的类，就是为了让这类判断只有一份实现。

写新代码前先搜一遍：还有谁在做同样的事。修完 bug 再搜一遍：还有谁会犯同样的错。

### 回退把失败藏起来

```java
try {
    走新路径;
} catch (Exception ignored) {
    退回旧路径;   // 新路径一次都没成功过，也没人知道
}
```

回退要留痕迹：写日志，或者在界面上说明用的是备用方案。

### 从桌面打开自动进网页（zzy.8 的坑）

这个功能修过两次，两次的原因都是「判据只在一个地方算」：

- 第一版只在 `savedInstanceState == null` 的分支里算一次。手机上进程经常被系统回收，用户点桌面图标时大多是「带着已保存状态重建」或「回前台收到新的启动 Intent」，那条分支根本不执行 —— 表现就是停在原生启动页。现在这次「打开」记在 `MainActivity.directWebArmed`，随 `savedInstanceState` 恢复，`onNewIntent` 里重新武装，四条路径（冷启动 / 重建 / 回前台 / 环境准备完回来）都调同一个幂等的 `LaunchFragment.requestDirectWeb()`。
- 第二处是环境准备：覆盖更新后第一次打开要先跑 `ExtractActivity`，它回主界面时用的是自己的 Intent（没有 `CATEGORY_LAUNCHER`），所以「从桌面打开」这个判断会丢。现在由 `EXTRA_DIRECT_WEB` 显式带过去。

改这里时注意：`directWebArmed` 只能在「真的进了网页 / 用户点留在主界面 / 放弃重试」三种情况下清掉（`onDirectWebFinished()`），否则旋转屏幕或切主题重建界面时会被反复带进网页。

### 只看退出码

`pnpm install` 返回 0，不代表插件已经注册进配置。做完一件事，要去检查它应该产生的结果：插件在不在清单里，备份里有没有对话。

### 转义层数

在 Java 里拼 shell 命令，要经过 Java 字符串、shell、`printf` 好几层转义，很容易多一个或少一个反斜杠。能不转义就不转义，拼完实际跑一遍看输出。参数用 `ShellQuote`。

### 在主线程做 IO

主线程卡住几秒，系统会弹「应用无响应」。文件、网络、执行命令都放后台线程。

### 改成异步以后的共享状态

把某件事挪到后台线程以后，要回答三个问题：谁还会同时读写这份数据？失败回滚时会不会又触发监听器？同一个操作执行两次会怎样？

### 只用手写样本测试

涉及外部格式（压缩包、网络响应、别人的配置文件）时，要拿真实样本跑一遍。手写的路径字符串能过，不代表真实的 GitHub 压缩包也能过。

### 进程和容器生命周期

- Termux proot 带 `--kill-on-exit`，调用结束时它下面的进程会一起被结束；proroot 没有这个参数，杀掉启动器以后容器里的 node 还活着。所以停止 dsh 要按 pid 文件和进程身份精确结束（`WebProcessManager`、`util/WebProcSel`），不能靠杀启动器。
- 容器 bind 了宿主的 `/proc`，能看到手机上的其他进程。`pkill -f node` 这种按名字杀的写法可能连 App 自己一起杀掉。不要按名字、端口或裸 PID 杀进程。
- 停止前要写 `/root/.dsha-stopped`，否则看门狗会马上把进程拉起来。

### 文件系统

proot 先检测私有目录支不支持硬链接，只有不支持时才加 `--link2symlink`（`runtime/ContainerRuntime.Proot.baseArgv`），因为这个模拟会影响 dsh 的写文件工具。各厂商系统在链接和存储权限上表现不一致，能用复制就别用链接。

## 6. 和 AI 协作

- 一轮改动做完、验证过再提交。提交信息用中文，带 `type:` 前缀，写清根因和取舍，不要只写「修复 bug」。
- 卡住的时候先查有没有现成的做法，例如插件作者的说明、历史提交记录，别一直靠猜。
- 以前好用、现在坏了的功能，去翻提交历史，用二分法找出是哪次改坏的。
- 提需求时写清位置、动作、结果。例如：「在插件卡片上加一个导出按钮，把这个插件导出成单个文件，放到 `Download/DSHA/` 下」。只有一个模糊想法时，就把要解决的问题讲清楚，让 AI 先查原因。

判断 AI 做得对不对，不需要会写代码：

- 问它验证了什么。说不出具体验证方法的，多半没验证。
- 加了功能，单测数应该跟着增加。
- 提交说明里应该有「为什么」。
- 它说「需要真机验证」时要当真：界面、权限、文件系统和厂商系统的行为，电脑上验证不了。
- 它主动纠正自己之前的判断，是好事。

## 7. 发版与签名

发版流程见 [HANDOVER.md](../HANDOVER.md) 第 2 节：更新 `CHANGELOG.md` 和 `.github/RELEASE_NOTES.md`，推送，然后在 Actions 里手动运行 Build APK 并勾选 `publish`。不需要推送标签，`tag` 留空时工作流会自动在最新的 `…-zzy.N` 上加 1。

- 所有发行版都用同一把 CI 密钥签名（Secrets `DSHA_CI_KEYSTORE_B64` / `DSHA_CI_KEYSTORE_PASSWORD`，证书指纹见 HANDOVER.md 第 3 节）。Android 只允许同签名覆盖安装，换了密钥，用户只能卸载重装，数据会丢。加密备份和恢复步骤见 [.github/signing/README.md](../.github/signing/README.md)。
- `app/build.gradle` 里的 `publish` 签名配置和 `verifyPublishCertificate` 任务认的是**本 App 自己的发布证书**（指纹见 HANDOVER.md 第 3 节）。CI 用 `-x verifyPublishCertificate` 跳过它。
- 发布包名是 `zzy.dsha.Kotlin`（CI 注入）；本地构建的包名是 `com.dsh.client`。两者可以同时安装。

## 8. 卡住了怎么办

| 情况 | 先做什么 |
|---|---|
| 编译不过 | 用 `build.sh` 或仓库自带的 `gradlew`，检查 JDK 17 和 SDK 版本（BUILD.md 第 1 节） |
| 单测红了 | 先搞清是代码错了还是测试错了，两种都可能 |
| 电脑上对、真机上不对 | 多半是文件系统、权限或厂商系统的差异。选不靠运气的实现，比如用复制代替链接 |
| 怎么改都不对 | 翻提交历史，找最后一次正常的版本，二分定位 |
| 不确定该不该做 | 回到第 2 节，dsh 是不是已经有了 |

## 9. 两条原则

- 每个判断只有一份实现。
- 说「完成」必须有能复现的证据。
